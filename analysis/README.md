# 남는돈 D테스트베드 분석 도구 (3판)

원본: 팀 Google Drive 의 `dtestbed_v3_2026-09-21.zip`. 실제 데이터 없이 코드와 기본 설정만 가져왔다.
저장소 루트에서 `npm run setup` 후 `npm run analysis -- selftest` 로 실행한다.
환경 설치와 노트북 사용은 [개발 환경](../docs/development.md#분석-환경)을 참고한다.
아래 `python run.py ...` 는 `npm run analysis -- ...` 로도 실행할 수 있다.
`demo` 는 지정한 결과 폴더를 지우고 가짜 자료를 생성하므로 실제 자료·결과 경로를 주지 않는다.

금결원 이체 자료로 **원천 거래 전량 추적**과 **월 단위 반복 출금 후보 탐지**를 하고, 개발용·평가용 계좌를 나눠 **독립 검토로 채점**하는 도구입니다.

1. **인터넷 없이 돕니다.** 파이썬 3.8 이상만 있으면 되고 따로 설치할 것이 없습니다 (표준 라이브러리만 씀)
2. 결과는 「반복 출금 **후보**」입니다. 사업 지출이나 고정비로 확정하지 않습니다
3. 평가표의 숫자는 「사람이 판정한 월 반복 패턴과의 일치도」입니다. 과거 기록에서 반복을 찾는 성능이며 앞으로의 출금을 예측하는 성능이 아닙니다
4. 정밀도 85%·재현율 70%는 **사전 목표값**입니다. 목표와 견주는 값은 **가중 점추정치**이고, 참고 구간과 판정 불가 비율을 함께 봅니다
5. 검토 방식은 설정 한 줄로 고릅니다. 다만 **설정만 바꾼다고 독립 검토가 되지는 않습니다.** CTO가 실제로 참여하고, 규칙 개발에 관여하지 않고, 예측을 보지 않는 절차를 지킬 때만 `reviewer_mode: independent`(재판정 20%는 두 번째 검토자 몫), 대표 혼자면 `self`(내부 평가, 평가표에 독립 검증 아니라고 찍힘). 지금 기본값은 `self`이고 CTO 참여를 확인 중입니다

2판(GPT 1차 검토): 청구와 실제 출금 분리, 동결을 표본보다 먼저, 거래 1건 단위 모집단과 U 민감도, 말일 기준·묶음 2개·빠진 달 규칙, 보조 근거 2단계 검토, 채점 기록.

3판(GPT 2차 검토, CTO 부재): 매주·수시 판정을 묶음별로, 같은 달 기준일 근처에서는 흔한 금액대를 먼저 고름, CMS 「실패 없음」은 기본 미해결, 분할 시점 평가 계좌 목록 지문, 대표 단독 판정과 14일 뒤 재판정, 구간을 「참고 구간」으로 낮춤, `compare` 명령.

3판 보완(GPT 3차 검토): 매주 확인의 금액 범위를 고정·변동 금액에서 같은 기준으로, 거래 없는 달은 0건으로 셈, 시도 최대 3번·인정 묶음 최대 2개, CMS 추정을 켜려면 근거 기록 필수, `dev-sheet` 점검지와 `compare`의 맞음·틀림·놓침.

## 1. 처음 한 번

```
python run.py demo       # 가짜 샘플로 처음부터 끝까지 (3초 안팎). 끝에 평가표가 나오면 설치 끝
python run.py selftest   # 자체 점검 17개
python run.py init       # 개발용·평가용 분리 기준(솔트)을 정한다. 한 번만. 이후 바꾸지 않는다
```

`demo`의 숫자는 가짜 데이터라 의미가 없습니다. 도구가 끝까지 도는지만 봅니다.

## 2. 실제 데이터가 들어온 뒤 순서 (이 순서는 코드가 강제합니다)

`--data` 에는 테이블 이름(HF_TRNS_TRAN 등)이 파일 이름에 들어간 csv/txt 파일이 있는 폴더를 줍니다.

| 주차             | 명령                                                      | 누가                     | 나오는 것                                                                                                                                                                                                  |
| ---------------- | --------------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1~2              | `profile --data D`                                        | 대표                     | 2주차 현황: 관측기간, 연결률, 다중대응률, 금액 구간, 자금구분 04 비중                                                                                                                                      |
| 1~2              | `reconcile --data D`                                      | 대표                     | 원천 행 추적표(반영·제외·미해결)와 실제 거래 통합표(확정·명세 근거 추정)                                                                                                                                   |
| 1~2              | `split --data D --note "..."`                             | 대표                     | **개발 시작 전에.** 개발용·평가용 계좌 목록과 평가 계좌 목록 지문                                                                                                                                          |
| 3~8              | `detect`, `dev-sheet`, `compare`, `thresholds`            | 대표                     | **개발용 계좌만** 보고 규칙 숫자(config/params.json)를 고친다. 점검지에 사람이 **거래마다** R·N·U를 적으면 선택지별 맞음·틀림·놓침이 나온다. 60쌍은 규칙 선택용이며 성능 근거가 아니다. 고른 이유는 문서에 |
| 1~8              | config/guideline.md                                       | 대표 (+ Claude·GPT 검토) | 판정 지침을 개발용 예시로 확정                                                                                                                                                                             |
| 8                | `freeze --data D --note "..."`                            | 대표                     | 규칙·설정·지침·코드·데이터·분할 기록 동결. **표본보다 먼저**                                                                                                                                               |
| 8                | `sample --data D`                                         | 대표                     | 평가표본, 1차 검토지(예측·보조 근거 없음), 재판정용 20%(순서 섞음)                                                                                                                                         |
| 8~9              | 며칠 쉬고 1차 판정 → `commit-labels`                      | 대표                     | 1차 지문. 본 점수는 이것으로 고정                                                                                                                                                                          |
| 1차 지문 14일 뒤 | 재판정 → `commit-labels --stage recheck`                  | 대표                     | 자기 일치도                                                                                                                                                                                                |
| 그 뒤            | `aux-review --data D` → 2차 → `commit-labels --stage aux` | 대표                     | 보조 근거를 본 뒤 바꾼 판정과 이유                                                                                                                                                                         |
| 10~11            | `evaluate --data D`                                       | 대표                     | 평가표 (한 번만. 다시 돌리려면 `--rerun-reason`)                                                                                                                                                           |
| 언제든           | `history`                                                 | 누구나                   | 분할·동결·표본·지문·채점 기록                                                                                                                                                                              |

재판정에 14일이 걸리므로, 12주 일정에서 **동결은 늦어도 8주차**에 해야 합니다. 이 날짜가 사무국의 최종 보고·반출 신청 마감에 맞는지 확인합니다. 14일은 기억의 영향을 줄이려는 **내부 운영 기준**이지 독립성을 보장하지 않습니다.

규칙이 잘 안 맞을 때 시험용으로 `--limit 100000` 처럼 앞부분만 읽을 수 있습니다.

## 4. 코드가 막아 주는 것 (변경 추적)

같은 계정에서 파일과 기록을 함께 고칠 수 있으므로, 아래는 **실수와 변경을 드러내는 장치**이지 조작을 원천 차단하는 장치는 아닙니다.

1. 탐지는 자금구분(FND_TYPE)을 **볼 수 없습니다** (`tb/detect.py`의 `ALLOWED`)
2. `detect`·`compare`는 **개발용 계좌만** 봅니다
3. `freeze`는 분할 기록, 목표 기준, 판정 지침이 없으면 멈춥니다. 두 번 동결하지 않습니다
4. 처음 기록한 분리와 지금 분리가 다르면 `split`이 멈춥니다
5. `sample`은 **동결 뒤에만** 됩니다. 두 번 뽑지 않습니다
6. 동결 뒤 규칙 숫자·설정·판정 지침·코드·데이터·분할 기록 중 하나라도 바뀌면 표본과 채점이 멈춥니다
7. 검토지가 지문을 남긴 뒤 한 글자라도 바뀌면 채점이 멈춥니다. 지문은 덮어쓰지 않습니다
8. 재판정 지문은 1차 지문 14일 뒤에만 받습니다. 보조 근거 검토지는 재판정 뒤에만 열리고, 바꾼 줄에 이유가 없으면 지문을 남기지 않습니다
9. 채점은 한 번입니다. 다시 돌리려면 이유를 적어야 하고, 평가표에 「재채점」과 이유가 찍히며, 모든 실행이 기록에 남습니다

## 5. 실제 파일이 명세서와 다를 때

명세서는 2022년 9월 판입니다. 실제 파일의 컬럼 이름이 다르면 `config/columns.json`의 **오른쪽 값만** 고칩니다. `profile`의 「없는 컬럼」 칸에 어긋난 이름이 나옵니다.

## 7. 탐지 규칙이 보는 것

한 짝(출금계좌→입금계좌)마다:

1. 관측 달이 모자라면 제외
2. 기준일: 「매달 같은 날」과 「매달 말일」 중 더 잘 맞는 쪽 (정해진 순서로 고름)
3. 기준일 가까이에서 달마다 하나씩 골라 묶음을 만든다. 같은 달 근처에 여러 건이면 가장 흔한 금액대를 먼저 고른다(보조 기준일 뿐 월세를 가려내는 근거는 아님). 한 짝에 묶음 둘까지 (예: 5일 월세, 25일 관리비)
4. 묶음마다, 하나로 줄이기 전에 그 묶음 금액 범위의 거래가 달마다 몇 건인지 센다. 금액 범위는 고정 금액이면 최빈 구간 ±1, 금액 변동을 허용하면 묶음 거래의 최소~최대 구간 ±1. 묶음의 첫 달~끝 달 전부를 세고 **거래 없는 달은 0건**으로 넣는다. 가운데 값 3 이상이면 매주·수시 반복으로 그 묶음만 제외
5. 묶음 찾기는 **최대 3번 시도**하고, 통과한 묶음은 **최대 2개**까지 인정한다. 떨어진 시도가 쓴 거래는 빼고 다음 시도를 한다 (매주 소액이 떨어진 뒤 같은 짝의 월세를 따로 본다). 「쓴 거래」는 매주·수시로 떨어졌으면 빈도를 센 범위 전체, 다른 이유면 달마다 고른 거래만. 뺀 원천 행 번호와 이유는 내부 후보 목록(`후보_개발용.csv`의 dropped 칸)에 남는다
6. 묶음마다 날짜가 맞는 달 비율, 이어진 달의 간격이 한 달인 비율, 빠진 달 비율(출금 계좌 관측의 첫 달·끝 달은 일부만 관측됐을 수 있어 빼고 셈), 금액 구간이 같은 비율
7. 금액이 흔들리는 흐름은 `allow_variable_amount`를 켜면 「변동 금액」 후보로, 끄면(기본) 제외

비율이 관측 달 수별로 실제 몇 달을 뜻하는지는 `python run.py thresholds`.

## 8. 알아 둘 한계

1. 표준 파이썬만 쓰므로 큰 자료에서는 메모리가 많이 듭니다. 가짜 샘플 **약 25만 줄에 검산+탐지 약 14초·메모리 0.75GB** (2026-09-21 측정). 수백만 줄부터 VDI 메모리가 모자랄 수 있습니다. **인터넷이 열린 동안** `python -c "from tb.sample_data import make; make('data/big', n_payers=40000)"`로 큰 샘플을 만들어 VDI에서 재 보고, 모자라면 pandas판을 그 기간에 준비합니다
2. 주·분기 반복은 아직 안 봅니다. 월 단위부터 검증합니다 (계획서)
3. 계좌 일련번호로 상대를 묶으므로, 여러 계좌를 쓰는 같은 거래처는 다른 상대로 봅니다
4. 한 짝에 반복 흐름이 셋 이상이면 둘까지만 잡습니다
5. **매주 지급과 월세가 같은·이웃 금액 구간**이면 금액만으로 구별하기 어렵고, 지금 규칙에서는 월 반복을 놓칠 수 있습니다 (날짜 패턴에는 구별할 정보가 남아 있을 수 있음)
6. 평가표의 구간은 계좌 단위 재표집 근사값입니다. 층별 추출 설계를 완전히 반영한 검증된 95% 신뢰구간이 아닙니다
7. 대표 단독 판정(`reviewer_mode: self`)이면 판정자가 규칙 개발자와 같은 사람입니다. 자기 일치도는 독립 검증이 아닙니다

## 9. 앱 자료로 다시 검증하기 (테스트베드 밖)

```
python run.py app-check --file 앱자료.csv
```

`앱자료.csv`는 세 칸: 날짜, 상대(앱이 정리한 거래처 글자), 출금액. 원 단위 금액은 금결원 자료와 같은 구간으로 바꿔서 봅니다.
