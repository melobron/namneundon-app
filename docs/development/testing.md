# 테스트

**사용자가 보는 화면 글자와 계산 숫자가 바뀌지 않았는지** 지키는 안전망 테스트다.
실제 크롬(Playwright)으로 `app/` 을 그대로 열어 사용자처럼 누르고, 결과를 저장해 둔 스냅샷과 비교한다.

## 돌리는 법

```bash
npm test                 # 불러오는 순서 검사(npm run check) → playwright test
npx playwright test tests/ledger.spec.mjs   # 파일 하나만
npm run test:prod        # 운영 주소(app.namneundon.com)를 같은 테스트로 검사
```

처음이면 [setup](setup.md) 의 `npm run setup` 을 먼저 한다. 테스트는 `tests/serve.mjs` 를 스스로 띄운다(포트 4173).

## 무엇을 지키나

| 파일                         | 따라가는 길                                                                                       | 비교하는 것                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `tools/check-load-order.mjs` | (`npm test` 가 먼저 돌린다) 파일마다 불러오는 순간 실행되는 코드                                  | 아직 안 불러온 파일의 이름을 쓰는가                                                               |
| `tests/demo.spec.mjs`        | 앱 열기 → 예시 먼저 보기 → 달마다 · 1년 · 예상 잔액 그래프 · 자세히                               | 예시 거래 2,363건의 계산 숫자 전부(`numbers.json`), 화면 글자                                     |
| `tests/upload.spec.mjs`      | 은행 엑셀 올리기 → 매장 이름 → 대표자 → 거래처 20곳 분류 → 목표일 → 결과 → 새로고침 → 이어서 보기 | 단계마다 화면 글자, 계산 숫자, 브라우저 저장 자료(`storage.json`), **되살린 숫자 = 저장 전 숫자** |
| `tests/ledger.spec.mjs`      | 모든 달 × (자르지 않음, 1 · 10 · 15 · 22일)                                                       | 월초 + 들어온 돈 − 나간 돈 = 월말                                                                 |
| `tests/security.spec.mjs`    | 이름에 HTML 이 든 파일을 같이 올리기                                                              | 파일 이름이 글자로만 보이고 스크립트가 돌지 않는다                                                |

공통 조건 (`playwright.config.mjs`, `tests/helpers.mjs`):

- 시계는 **2026-09-23 10:00 (서울)** 로 고정한다. 앱이 오늘 날짜를 쓰는 곳이 있다.
- 화면 너비 390px(휴대폰), 한국어 · 서울 시간대.
- 은행 엑셀은 예시 거래(`DEMO_TX`)로 만든 대역(`국민은행_거래내역.xlsx`, 한 양식)이다. **실제 은행 파일은 저장소에 넣지 않는다.**
- 콘솔 오류가 하나라도 나면 실패한다.

## 지키지 못하는 것

테스트가 통과해도 아래는 보장되지 않는다. 이 영역을 건드리면 직접 확인하고, 확인한 방법을 PR 에 적는다.

- **화면 모양.** 스냅샷은 글자와 숫자다. CSS · 배치 변화는 잡지 못한다 → 390px · 1280px 화면을 바꾸기 전 · 후로 비교한다.
- **여러 은행 양식 · PDF · 엑셀로 저장된 HTML.** 테스트 파일은 한 양식의 xlsx 뿐이다. 은행별 실제 파일 테스트는 [backlog](../backlog.md) C-1 · C-2.
- **다른 브라우저.** 크롬만 돈다. 사파리(아이폰) · 카카오톡 안 브라우저는 확인하지 않는다.
- **예상 잔액의 세부 규칙.** 예시 자료 한 벌의 결과 글자만 비교한다.
- **보안.** 파일 이름 한 경로만 지킨다. `innerHTML` 을 쓰는 다른 자리(약 70곳)는 따로 보지 않는다.
- 저장 공간이 넘칠 때, 시크릿 모드처럼 저장이 막힐 때.
- 운영 배포 뒤의 상태 — 자동 배포가 `npm run test:prod` 로 따로 확인한다 ([deployment](deployment.md)).

## 스냅샷을 다루는 법

| 변경 종류                                     | 스냅샷                                                                                              |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **리팩토링** · 문서 · 도구 (동작을 안 바꾼다) | **그대로여야 한다.** 바뀌면 코드가 틀린 것이다. 스냅샷을 고치지 않고 코드를 고친다                  |
| **일부러** 화면 글자 · 계산을 바꿨다          | 바뀐 줄이 의도한 것뿐인지 확인한 뒤 `npm run test:update`. PR 에 무엇이 왜 바뀌었는지 적는다        |
| 저장 자료(`storage.json`)가 바뀐다            | 저장 형식 변경이다 — 사용자와 먼저 정한다 ([결정 0003](../decisions/0003-storage-compatibility.md)) |

**테스트를 통과시키려고 스냅샷을 새로 찍지 않는다.** 스냅샷 갱신은 「이 변화가 맞다」는 판단이 먼저 있어야 한다.

## 실패하면

1. 실패 메시지와 `test-results/` 의 `*-actual.*` 를 `tests/snapshots/` 의 원본과 `diff` 로 비교한다. 실패한 테스트의 trace 도 `test-results/` 에 남는다 (`npx playwright show-trace <파일>`).
2. 바뀐 줄이 이번 변경으로 설명되는지 본다. **설명되지 않으면 코드를 의심한다.**
3. 이번 변경과 상관없이 실패하면 main 에서도 같은지 확인해(`git stash` 또는 다른 worktree) 원래 있던 문제인지 가린다. 보고할 때 둘을 구분한다.
4. 테스트를 건너뛰거나(`test.skip`) 기대값을 느슨하게 바꿔 통과시키지 않는다.

## 테스트를 더할 때

- 계산 규칙을 고치면, 고치기 **전에 실패하는** 테스트를 먼저 만든다 (`ledger.spec.mjs` 가 그 예다).
- 테스트는 앱의 전역 함수를 `page.evaluate` 로 부를 수 있다. 그 전역 이름은 테스트가 기대는 인터페이스가 된다.
- 새 테스트 파일은 위 표에 한 줄 더한다.
