# 제품과 계산 규칙

남는돈은 **1인 사업자·소규모 매장 대표가 사업으로 번 돈과 쓴 돈을 정리하는 웹앱**이다.
현재는 은행에서 내려받은 파일을 사용자가 올린다. 자동 은행 연동·로그인·서버 저장·세금 신고는 제공하지 않는다.
기록·정리를 먼저 개선하고 분석과 예측·계획을 확장한다는 제품 방향과, 이미 구현된 기능을 구분한다.
향후 기능의 우선순위는 Linear에서 관리한다.

## 현재 사용 흐름

업종 선택 또는 예시 보기 → 거래내역 파일 선택 → 잔액 검산 → 매장·대표자 입력 → 거래처 분류 → 결과.

- 파일 선택창은 `.xlsx`, `.xls`, `.html`, `.htm`, `.pdf`를 받는다. CSV는 지원한다고 안내하지 않는다.
- 여러 계좌·파일을 읽고 중복 파일과 겹치는 거래를 확인한다. 암호가 있는 PDF는 암호를 묻는다.
- 거래처를 묶고 일부를 자동 분류하며, 사용자가 분류를 수정한다.
- 결과는 월별 수입·지출·순이익, 1년 보기, 예상 잔액과 예정 지출이다. 현금 매출 등은 직접 입력할 수 있다.
- [확정] 한 달 결과의 차례는 ① 기간·자료 기준 ② 사업으로 번 돈·사업에 쓴 돈·계좌 순이익 ③ 예상 잔액과 그래프 ④ 상세 내역·계산 근거다. 예상이 보류돼도 ②는 보인다 (NAM-9, 2026-09-29 요한).
- [확정] 거래처 분류는 결과를 보는 조건이 아니다. 분류 화면에서 목표 전에도 「분류는 나중에 하고 결과 보기」로 결과에 갈 수 있다.
- 분류를 JSON으로 내보내고 불러올 수 있다. 이것은 거래내역·예정 지출까지 포함하는 전체 백업이 아니다.
- 저장된 매장은 같은 브라우저에서 불러온다. 마지막 매장을 자동으로 여는 것은 현재 동작이 아니다.
- 현재 업종 선택은 식당·카페·병원·치과·약국·미용실이다. 모바일 화면을 우선 고려한다.

## 자료를 다루는 약속

**파일 읽기·계산·저장은 사용자 브라우저 안에서 한다. 거래내역을 네트워크로 보내지 않는다.**
이 약속은 기존 제품 화면과 저장 코드에서 이어졌고 2026-09-25 공통 작업 규칙으로 명시됐다.
여러 기기 동기화나 서버 전환은 별도 제품 결정과 설계가 필요하다.
실제 은행 파일·개인정보·분석 결과는 저장소에 넣지 않는다. 테스트는 가짜 거래로 만든 자료를 쓴다.
테스트베드의 별도 Python 분석 도구는 [분석 안내](../analysis/README.md)를 따른다.

## 규칙을 읽는 법

이 문서는 두 종류를 구분해 적는다.

- **[확정]** 사용자(대표 · 운영자)가 제품 규칙으로 정한 것. 근거(문서 · 결정 · 코드 주석에 적힌 결정)를 단다.
- **[관찰]** 지금 코드가 그렇게 동작하는 것. 옳다고 확인된 규칙이 아니다 — 바꾸려면 먼저 사용자에게 묻는다.

코드 주석의 `★ N차` 는 회차별로 무엇을 왜 바꿨는지의 기록이다. 규칙의 배경은 거기에 더 자세히 있다.

## 거래 행

올린 파일은 거래 행(`UP.rows`)으로 바뀐다. 계산이 쓰는 칸:

| 칸         | 뜻                                                                                 |
| ---------- | ---------------------------------------------------------------------------------- |
| `at`       | 거래 시각 문자열 `YYYY-MM-DD` 또는 `YYYY-MM-DD HH:MM:SS`. 달은 앞 7글자(`YYYY-MM`) |
| `amount`   | 금액(원). **양수 = 들어온 돈, 음수 = 나간 돈**. 읽지 못하면 `null`                 |
| `balance`  | 그 거래 뒤 잔액                                                                    |
| `payee`    | 파일에 찍힌 거래처 원문                                                            |
| `residual` | 검산에서 설명되지 않는 차액 (사용자가 「적힌 금액이 맞다」고 답한 거래)            |
| `excelRow` | 원본 파일의 행 번호                                                                |

- [관찰] 은행마다 머리줄 위치 · 열 이름이 달라 머리줄과 열을 찾아 연결한다 (`core/parse-excel.js` `findHeader` · `mapColumns`). PDF 는 표로 바꾼 뒤 같은 길을 탄다 (`core/parse-pdf.js`).
- [관찰] 입금 · 출금이 한 열이고 「구분」 열로 방향을 나타내는 양식도 있다 (`dirFromKind` · `resolveSigns`).

## 순서와 검산

- [확정] **연번(NO)으로 순서를 정하지 않는다** — 시각과 반대로 매겨진 구간이 있다 (`core/verify.js` 머리 주석).
- [관찰] 앞 잔액 ± 금액 = 뒤 잔액이 이어지도록, 시각이 같은(60초 이내) 최대 6건까지는 순서를 바꿔 본다 (`FIX_WIN = 6`, `FIX_SPAN = 60`). 더 넓은 구간은 건드리지 않는다.
- [관찰] 그래도 끊긴 곳은 「확인 카드」로 사용자에게 묻는다. 답(`gap` · `stated` · `unknown`)은 `fc.breaks` 에 남아 같은 파일을 다시 올려도 다시 묻지 않는다.
- [확정] 「적힌 금액이 맞다」고 답한 거래의 설명 안 되는 차액(`residual`)은 **손익에 섞지 않는다** — 계산 밖 「확인 필요」로 보인다.

## 거래처와 분류

- [관찰] 거래처 이름을 다듬고(법인 표기 · 긴 숫자 · 연월 떼기 등) 같은 곳을 묶는다 (`core/classify.js`의 `canonName` · `buildMergeMap`, 앱의 연결 함수 `groupPayees`).
- [관찰] 일부는 이름 · 방향으로 자동 분류한다 (`autoCategory`). 자동 분류는 파일을 올릴 때마다 다시 돈다.
- [확정] **저장은 파일에 찍힌 원본 표기를 키로** 한다. 다듬은 이름으로 저장하면 다듬는 규칙을 바꿀 때 되살림이 조용히 0곳이 된다 (`pickPayload` 주석).
- [확정] **앱이 자동으로 정한 것은 저장하지 않는다.** 사용자가 손으로 정한 것만 남긴다 (46차 ⑥).
- [관찰] 거래처 확인은 금액 큰 곳부터 차례로 묻고, 한 번에 20곳(`UP_TARGET`)을 정하면 결과를 볼 수 있다.
- [확정] **금액 큰 순서** (2026-09-29 요한 확정). 결과 화면의 「사업으로 번 돈」 「사업에 쓴 돈」 항목 줄 · 거래처 목록, 1년 표의 펼친 세부 줄은 지금 고른 기간의 합계(절댓값)가 큰 순서다 — 43차의 「항목 고정 순서」를 대체한다. 항목 분류의 물을 차례 · 묶음 거래처 목록 · 보류 원인 질문 목록은 입금 · 출금을 상계하지 않은 절댓값 합계(`g.abs`)가 큰 순서다. 금액이 같으면 예전 차례를 지킨다. 정렬만 바꾸고 계산 · 분류는 그대로이며, 날짜별 거래내역과 그래프는 시간순이다. 비슷한 이름(「○○도 같은 곳인가요?」)과 묶음 카드는 그 카드가 떠 있는 동안만 관련 거래처를 모아 보이고 목록 차례는 바꾸지 않는다. 묶음을 되돌리면 빠졌던 곳은 남은 목록에 금액순으로 돌아간다(`queueInsertByAmount`). 예외로 둔 것: 앱이 넘긴 작은 출금 목록(출금만 묻는 목록이라 출금 합계 순) (`tests/sort-amount.spec.mjs`).

### 항목

- 고르는 항목 (`UP_CATS`): 사업 외 용도 · 식자재 · 주류·음료 · 인건비 · 월세 · 전기·가스·수도 · 세금 · 보험 · 세무기장료 · 소모품 · 수수료 · 대출 상환 · 대출 · 광고비 · 기타. 그리고 들어온 돈 쪽의 「매출」.
- [확정] **계산 밖 항목**(`UP_KEEP`): 「사업 외 용도」 · 「대출」. 통장 잔액에는 반영하지만 매출 · 지출 · 순이익에는 넣지 않는다.
- [확정] 대출은 **방향이 이름을 이긴다**: 들어온 줄은 「대출」(계산 밖), 나간 줄은 「대출 상환」(지출). 어느 이름으로 정해도 줄 방향으로 갈린다 (57차 ②, `sideOf`).
- [확정] 「사업 외 용도」도 방향으로 「내가 넣은 돈」 · 「내가 가져간 돈」으로 나뉘어 보인다 (63-3, `SIDE_ONLY`).
- [관찰] 저장된 항목 목록은 판 번호(`cv`)로 옛 차례를 읽어 지금 차례로 다시 세운다 (38차 · 57차). 항목을 넣고 빼면 이 변환도 함께 봐야 한다.

## 달마다 집계

계산은 `app/src/core/compute.js`의 `monthNumbersIn`, 앱의 연결 함수는 `14-compute.js`의 `monthNumbers`다.

| 값                  | 규칙                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| 들어온 돈 · 나간 돈 | [확정] **통장 합계와 정확히 같다.** 지출을 「매출 − 순증」으로 거꾸로 구하지 않는다                       |
| 매출                | 「매출」 항목의 순액 (카드 취소 · 환불 출금을 뺀 값). 통장에 실제 들어온 쪽은 따로 든다                   |
| 그 밖의 입금        | 매출이 아닌 입금 (환급 · 되돌려받은 돈)                                                                   |
| 지출                | 나간 돈만 항목별로 더한다                                                                                 |
| 아직 안 정한 돈     | [확정] **매출에도 지출에도 넣지 않는다** (35차 E). 대신 순이익이 움직일 수 있는 폭(아래 · 위)을 보인다    |
| 계좌 간 이체        | [확정] 사업의 매출 · 지출이 아니다. 거래처 항목과 상관없이 **줄 단위로** 가려 뺀다 (36차 4단계, `xferOn`) |
| 직접 넣은 금액      | [확정] 현금 매출 등 사용자가 적은 금액은 **손익에만** 넣는다. 잔액 · 검산에는 절대 넣지 않는다 (36차 J)   |
| 순이익              | 매출 + 그 밖의 입금 − 지출                                                                                |
| 월초 · 월말 잔액    | [확정] **계좌마다 따로 잡아 더한다.** 그 달 거래가 없는 계좌는 직전 잔액을 쓴다                           |

- [확정] **검산식: 월초 + 들어온 돈 − 나간 돈 = 월말.** 날짜를 잘라 계산할 때(`cutDay`, 「지난달 같은 기간」 비교)도 성립해야 한다 — `tests/ledger.spec.mjs` 가 모든 달 × (자르지 않음, 1 · 10 · 15 · 22일)로 지킨다.
- [관찰] 자를 때 월말은 `balanceAt(m, cutDay)` (그 날까지 계좌별 마지막 잔액의 합), 자르지 않을 때는 `monthCloseBalance(m)`. 둘 다 잔액을 찾지 못하면 0 으로 둔다. 2026-09-25 PR #12 에서 맞췄다 ([PR #12](https://github.com/melobron/namneundon-app/pull/12)).
- [관찰] 「진행 중인 달」은 자료의 마지막 달이면서 그 달 마지막 거래일이 월말보다 앞인 달이다 (`isRunning`). 그 달과 지난달을 견줄 때 지난달도 같은 날짜(`lastDayIn`)까지 자른다 (`17-result.js`).
- [관찰] 앱이 오늘 날짜를 쓰는 곳이 있어 테스트는 시계를 고정한다 ([테스트](development.md#테스트)).

- [확정] 여러 계좌 중 늦게 시작한 계좌 때문에 이전 달 월말과 다음 달 월초가 다를 수 있다. 계산은 유지하고 화면에 자료 시작 시점을 알린다 (2026-09-27 사용자 결정, `lateAccountsIn`, `tests/core/edge.spec.mjs`).

## 금액 · 날짜

- 금액은 원 단위 숫자이고 부호가 방향이다. 화면 표기(만 원 등)는 `02-text-loaders.js` 가 맡는다.
- 시간대는 한국(`Asia/Seoul`) 기준으로 본다. 테스트도 서울 시각으로 고정한다.

## 예상 잔액 (NAM-18)

2026-09-29 요한이 승인한 규칙이다. 계산은 `app/src/core/due.js`, 화면은 `16-due.js`다. 테스트는 `tests/core/due.spec.mjs`와 `tests/due-xfer.spec.mjs`에 있다.
Linear의 예전 내용(예: 「미분류 출금은 예측에서 뺀다」)과 다르면 이 절이 최신이다. 차이는 [인계 기록](../plans/nam-bundles-2026-09-29.md)에 적었다.

### 기간

- [확정] 기간은 묻지 않는다. **자료 기준일이 속한 달의 다음 달 말일까지** 본다 (`DUE_END_DAY` = 31, `nextDue`). 오늘 날짜·파일을 고른 날·다시 연 날로 늘리거나 옮기지 않는다.
- [확정] 자료 기준일은 모든 계좌에 잔액이 있는 마지막 날이다 (`commonAsOf`). 계좌마다 끝나는 날이 다르면 「여러 계좌를 함께 계산할 수 있는 ○월 ○일을 기준으로, ○월 ○일까지 예상했습니다」라고 적는다.
- [확정] 예상 종료일이 오늘보다 앞이면 머리를 「예상 · 과거 자료 기준」으로 바꾸고 날짜에 해를 붙인다. 계산 기간은 그대로다 (`dueIsOld`).
- [관찰] 예전에 고른 목표일(`dueDay`)은 `fc.picks` 의 `목표일` 에 그대로 읽고 쓰지만 기간에는 쓰지 않는다.

### 입금 · 출금

- [관찰] 예측 입금은 직전 30일 동안 「매출」로 분류한 거래의 평균이다. 매출로 분류한 환불 출금은 이 합에서 빠진다. 매출이 아닌 입금(대출·대표 입금·환급 등)과 아직 분류하지 않은 입금은 넣지 않는다 (`dueInflowIn`).
- [확정] 예측 출금은 지난 3개월 같은 구간(기준일부터 며칠째)의 날짜별 계좌 출금 평균이다. 사업 외 출금과 **아직 분류하지 않은 출금도 넣는다**. 확인된 계좌 간 이체와 확인 전 이체 후보는 넣지 않는다. 한 번만 있었던 출금도 같은 평균에 들어간다 (`dueTableBuildIn`).
- [확정] 예측에 넣는 것과 월별 사업 수입·지출·계좌 순이익은 별개다. 미분류 거래는 손익에 넣지 않는다.

### 보류 (실적은 늘 보인다)

보류되면 종료일 예상 잔액·다음 달 최저·참고 범위·그래프를 모두 내지 않는다. 사유가 여럿이면 함께 적는다. 하나를 끝내면 열린다고 약속하지 않는다 (`dueCardIn`, `dueHoldReasons`).

| 사유 | 조건                                                                     | 화면 안내와 할 일                                                                                                |
| ---- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 자료 | 첫 예상일조차 비교할 과거 구간이 3개가 안 된다 (자료 3개월 미만)         | 「예상 잔액을 보려면 3개월 이상의 거래내역을 추가해 주세요.」 · [거래내역 추가하기]                              |
| 이체 | 예측에 쓰인 비교 날짜에 확인 전 이체 후보가 있다 (분류 여부와 상관없이)  | 「예상 잔액을 보려면 계좌끼리 옮긴 돈인지 N건을 확인해 주세요.」 · [계좌끼리 옮긴 돈 확인하기]. N은 후보 쌍의 수 |
| 입금 | 직전 30일에 「매출」로 분류한 입금이 한 건도 없다                        | 미분류 입금이 있으면 「아직 매출로 확인된 입금이 없습니다. 미분류 입금 N건 중 매출이 있는지 확인해 주세요.」     |
|      |                                                                          | 입금이 없으면 「직전 30일에 들어온 돈이 없어…」, 모두 매출 밖이면 「…매출로 분류한 거래가 없어…」                |
| 잔액 | 기준일 잔액을 복원할 수 없는 계좌가 있다 (`dueUnknownAccsIn`, 102차부터) | 카드 대신 확인이 필요한 계좌와 자료 기간을 적는다                                                                |

- [확정] 매출 분류가 있으면 예상을 보이고, 직전 30일 미분류 입금의 건수·금액과 「아직 분류하지 않은 입금은 예상 입금에 넣지 않았습니다. 매출이 포함돼 있다면 예상 잔액이 낮게 계산될 수 있습니다.」를 붙인다. 건수를 「꼭 분류할 개수」로 부르지 않는다.
- [확정] 거래처 분류는 결과를 보는 조건이 아니다. 금액 기준 분류율 %는 그대로 보인다.

### 이체 후보에 대한 답

- [확정] 후보 한 쌍(나간 줄 → 들어온 줄)마다 세 가지 답이 있다. 기존 판별(`findTransfersIn`)을 그대로 쓴다.
  - 「계좌끼리 옮긴 돈입니다」: 이체로 확인한다. 매출·지출과 예측 출금에서 뺀다 (`takeXfer`).
  - 「계좌끼리 옮긴 돈이 아닙니다」: 후보에서만 뺀다. 분류는 그대로이고 일반 거래 규칙으로 계산한다. 사업 지출로 자동 분류하지 않는다 (`markNotXfer`).
  - 「나중에 확인」: 확인 전으로 되돌린다. 예상은 보류된다. 잘못 누른 답을 고치는 길이다 (`clearXferAnswer`).
- [확정] 답은 후보 한 쌍에 붙는다. 화면 안에서는 쌍 ID(두 줄의 `rowId`)로 들고 있다. 「계좌끼리 옮긴 돈입니다」 · 「아닙니다」 · 「나중에 확인」은 이번 화면에서 그대로 쓴다.
- [확정] **새로 읽은 파일에는 저장된 이체 답을 자동으로 붙이지 않는다** (검증방 지적 2026-09-29 세 번째). 파일 이름 · 시트 이름 · 은행 이름으로는 계좌를 가를 수 없다 — 서로 다른 두 국민은행 계좌가 둘 다 「국민은행_거래내역.xlsx」로 내려받아질 수 있다. 새 파일 읽기 · 보태기 · 분류 불러오기 뒤에는 이체 후보를 다시 묻는다(맞음 · 아님 모두). 되살리는 길은 이 기기에 저장한 거래내역(`fc.data`)을 그대로 다시 열 때 하나다 — 그 자료에 함께 남긴 쌍 ID(`fc.data` 의 `xfer: {ok, no}`)로만 붙인다 (`xferDataAnswers` · `applyXferFromData`). `fc.data` 는 원래 금액 · 잔액을 담는 이 기기 전용 통이고, 계좌번호는 넣지 않는다. `fc.picks` 의 `xferOk` · `xferNo`(쌍 저장 키, 금액 없음)에는 새 답을 더 남기지 않고, 예전 판이 남긴 키만 버리지 않고 들고 간다.
- [확정] 옛 칸 `xfer`(줄 키: 날짜 · 은행 이름 · 행번호)는 계좌를 가를 정보가 없어 자동으로 적용하지 않는다. 지우지 않고 들고 있다가 그대로 다시 남긴다 — 119차에서 이체를 확인해 둔 사용자는 한 번 다시 확인해야 하고, 그 전까지 그 거래는 매출 · 지출에 다시 들어간다.

### 다음 달 최저 예상 잔액

- [확정] 다음 달 최저 예상 잔액은 다음 달 1일~말일 안에서만 고른다. 이번 달이 더 낮아도 다음 달 값을 쓴다. 계산은 같은 날 출금을 입금보다 먼저 반영한 값이다 (`dueNextMonthLowIn`). 화면의 라벨 · 툴팁에는 「입금 전」을 적지 않고, 그 가정은 「자세히」에 「같은 날에는 출금이 입금보다 먼저 발생한다고 가정합니다.」 한 줄로만 둔다 (2026-09-29 요한 확정). 그래프 금액표는 「계산상 최저 예상 잔액 ○원」, 날을 고른 상세는 값이 둘이면 「그날 가장 낮은 예상 잔액」 · 「그날 마지막 예상 잔액」, 같으면 「예상 잔액」 한 줄이다.
- [확정] **카드와 그래프는 같은 계산 결과를 쓴다** (2026-09-30 요한 최종, `dueNextMonthLow`). 예상 카드 맨 위 큰 칸: 「○월 ○일 자료 기준 · ○월 최저 예상 잔액」 / 「75,374,590원」(원 단위) / 「9월 10일로 예상됩니다」. 그래프 금액표 「계산상 최저 예상 잔액 ○원」과 같은 날 · 같은 금액이다. 음수도 그대로 적고, 음수면 「음수는 예상대로 돈이 들어오고 나갈 경우, 계좌의 돈이 부족할 수 있다는 뜻입니다.」를 한 줄 더한다.
- [확정] 반드시 두는 문구: 「과거 거래를 바탕으로 계산한 예상이며, 실제 날짜와 잔액은 달라질 수 있습니다.」 「예상에 없던 큰 입출금은 반영되지 않을 수 있습니다.」 적중률 · 신뢰구간 · 안전 보장이라는 말을 쓰지 않는다.
- [확정] 월말 예상 잔액은 보조 정보로 「자세히」의 「월말(○월 ○일) 예상 잔액」 줄에 둔다. 그래프의 월말 금액표는 작은 회색 테두리 표이고, 다음 달 계산상 최저 점을 가장 크게(채운 점 + 고리 · 큰 금액표) 보인다. 그래프의 날짜별 값은 「계산상 · 예상」으로 부른다.
- [확정] 최저값을 표시할 수 있는가는 다음 달 최저값이 계산됐는가(다음 달에 닿았는가 · 비교 자료 · 기준일 잔액)와 기존 보류 조건(자료 · 이체 · 입금)으로만 정한다. 표시할 수 없으면 큰 칸에 월말 값을 올리지 않고 까닭과 할 일(「더 이전 기간의 거래내역을 추가해 주세요.」 등, 올린 파일이 있으면 「거래내역 추가하기」 단추)을 적는다 (`dueNoLowWhy`). 이때는 최저에 기대는 특정 날짜 · 부족 금액 · 경고 아이콘 · 최저 문장도 함께 내지 않는다(검증방 지적 2026-09-29) — 자료 범위에 관한 주의(공통 기준일 · 계산이 잘린 날)는 그대로 둔다. 월말 값은 계산된 카드일 때만 「자세히」에 둔다. 보류 조건은 그 앞에서 보류 카드로 갈려 우회하지 않는다.

#### 내부 검토 기록 — ±30% 임시 참고 범위 (화면에서 뺌)

- [기록] 2026-09-29 요한 승인으로 카드 큰 칸에 「하한 ~ 상한 (임시 참고 범위)」와 주 단위 시기(최저일이 든 월~일, 다음 달 안으로 자름)를 보였다. 범위 = 계산상 최저 ± 다음 달 예상 출금 합계 × 0.3 (±50%에서 변경). 예시 자료에서 48,507,077원 ~ 102,242,103원, 9월 4일~10일.
- [기록] 근거는 전달받은 118차 최저 잔액 분석 보고(매장 4곳 · 32창 · 중앙값 11.7% · ±30% 안 27/32)였다. 그 분석의 스크립트 · 자료 · 오차율 분모는 저장소에서 찾지 못했고, 현재 규칙으로 다시 검증하지 않았다.
- [기록] 2026-09-30 요한 최종 변경으로 카드의 범위 · 주 단위 날짜 · 「임시 참고 범위」 문구 · 범위 설명을 모두 뺐고, 계산 함수(`dueNextMonthRangeIn` · `dueWeekOf`)도 코드에서 뺐다. 다시 쓰려면 이 기록과 git 이력(`c3c3b3f` 전후)을 본다.

### 금액 표시

- [확정] 예상값도 원 단위로 보인다 (2026-09-29 요한 확정 — 앞서 승인한 만원 표기를 취소). 만원 반올림 · 「1만원 미만」 · 「부족액 1만원 미만」을 쓰지 않는다. 원 단위는 계산값의 표시 정밀도일 뿐 예측 정확도가 아니므로 「예상」과 한계 안내는 그대로 둔다 (`dueWon`).
- [확정] 그래프 축은 읽기 쉽게 단위를 줄여 쓰되(만원 · 억원) 축 제목에 단위를 적는다. 그래프의 날짜별 값 · 금액표는 원 단위다.

## 저장 자료

저장 이름·형식 변경은 사용자와 먼저 정하고, 옛 자료를 읽어 옮기는 코드를 함께 만든다.
분류가 조용히 사라지는 일을 막기 위해 이전 판 번호(`cv` · `v` · `dv`)의 호환성을 유지한다.

브라우저 `localStorage` 에만 저장한다. **이름 · 형식을 바꾸지 않는다** (기존 사용자 분류를 다시 읽지 못하는 사고를 막기 위한 호환성 원칙). `<매장>` 은 매장 이름(없으면 `(기본)`).

| 저장 이름                                      | 담는 것                                                                     | 금액     | 내보내기  |
| ---------------------------------------------- | --------------------------------------------------------------------------- | -------- | --------- |
| `fc.picks.<매장>`                              | 사용자가 정한 거래처 분류 · 항목 목록 · 업종 · 목표일 · 이체 답 등          | **없음** | 들어간다  |
| `fc.manual.<매장>`                             | 직접 적은 금액 (현금 매출 등)                                               | 있음     | 안 들어감 |
| `fc.banks.<매장>`                              | 계좌를 부르는 이름                                                          | 없음     | 안 들어감 |
| `fc.data.<매장>`                               | 거래내역 그 자체 (다시 열 때 이어 보기)                                     | 있음     | 안 들어감 |
| `fc.plan.<매장>`                               | 예정 지출                                                                   | 있음     | 안 들어감 |
| `nd_lastrun.<매장>`                            | 마지막으로 분석한 날짜 `YYYY-MM-DD` 하나 (2026-09-19 결정)                  | 없음     | 안 들어감 |
| `fc.last`                                      | 마지막으로 남긴 매장 이름 (지금은 저장만 하고 자동으로 열지 않는다, 97차 ①) | 없음     | —         |
| `fc.breaks`                                    | 확인 카드 답 (날짜 + 원문 이름 + 행 번호 → 글자 하나)                       | 없음     | —         |
| `fc_use`                                       | 사용 기록 (연 날 · 올림 · 찍기 횟수 등)                                     | 횟수     | —         |
| `fc.font` · `fc.a2hs.later` · `fc.inapp.later` | 글씨 크기 · 설치 안내 · 카톡 안내 「나중에」                                | 없음     | —         |

- [확정] **`fc.picks` 에는 금액을 담지 않는다.** 저장 전에 `hasNumber` 검사로 막는다(판 번호 · 곳 수 · 목표일 · 순번만 예외). 「복사해서 남에게 넘기는 값에는 금액이 없다」는 원칙이다 (36차 J, `savePicks`).
- [확정] 금액이 든 자료는 통을 따로 둔다 (`fc.manual` · `fc.data` · `fc.plan`). 이 통들은 이 기기 안에만 있고 **읽어서 네트워크로 보내는 코드가 없다** (91차 ①).
- [관찰] 저장이 막힌 브라우저(시크릿 모드 등)에서도 앱은 메모리로 그대로 돈다 (`LS_OK`).
- [관찰] 매장 이름을 바꾸면 `renameStore` 가 저장 자료를 새 이름으로 옮기는 처리를 한다. 모든 실패 상황에서 데이터 보존이 보장된다는 뜻은 아니다. 저장 관련 미해결 이슈를 변경 전에 확인한다.
- [확정] 브라우저 저장소는 **주소(origin)마다 따로**다. 앱 주소를 바꾸면 옛 주소의 자료가 새 주소에서 안 보인다 — 실사용자가 있을 때 주소를 바꾸려면 자료 옮기기가 먼저다 ([주소 변경](development.md#주소-변경과-복구)).

## 미확정 · 문서화 안 된 것

- 예정 지출 편집·반복 출금 연결 규칙 (`core/due.js` 의 `duePlan*`, `16-due.js` 의 예정 지출 화면) — 아직 이 문서에 정리하지 않았다. 바꾸기 전에 코드와 `due-plan.spec.mjs` 스냅샷을 읽는다.
- 자동 분류 규칙(`autoCategory`)의 전체 목록과 근거.
- 테스트베드 반복 출금 탐지의 정밀도 85%·재현율 70%는 사전 목표이며, 제품의 실측 성능이나 미래 출금 예측 정확도가 아니다 ([분석 도구의 평가 한계](../analysis/README.md#8-알아-둘-한계)).
