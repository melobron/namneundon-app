## 문제와 원하는 결과

대표님이 매장 이름을 바꿀 때 분류·현금 입력·계좌 이름·거래내역·예정 지출이 함께 이동한다.
현재 코드는 새 이름으로 저장하지 못해도 이전 자료를 지우고 성공한 것처럼 화면 이름을 바꾼다.
이미 있는 다른 매장 이름을 입력해도 그 매장 자료를 덮어쓴다.

성공할 때는 모든 자료를 새 이름으로 다시 열 수 있어야 하고, 실패할 때는 원래 매장으로 계속 사용할 수 있어야 한다.
두 이슈는 원인이 다르지만 같은 함수와 저장 버튼을 다루므로 **한 구현 PR, 서로 구분된 회귀 테스트**로 진행한다.
매장 합치기·기존 자료 덮어쓰기 확인 버튼은 만들지 않는다.

## 구현 방법

### 1. 저장소와 화면의 역할

저장소에 직접 접근하는 코드는 계속 `00-storage.js`에만 둔다.
여기에 실패를 숨기지 않는 원문 읽기와 여러 키 복사·확인을 지원하는 작은 함수를 추가할 수 있다.
기존 `lsGet`의 전체 앱 계약을 바꾸지 않는다. 이전 오류로 `LS_OK`가 이미 false일 수 있으므로 그 값만으로 이번 읽기의 성공 여부를 판단하지 않는다.

`renameStore`는 준비 → 저장·검증 → 화면 상태 반영의 순서를 관리한다.
반환값은 성공·변경 없음·이름 충돌·읽기 실패·저장 실패·정리 경고를 구분하도록 한다.
정확한 함수 이름·객체 필드는 구현자가 정하되, 화면 호출부가 실패를 놓칠 수 없는 계약으로 만든다.

### 2. 이름과 이동 대상

이름 비교는 기존 키 함수가 만드는 저장 식별값을 기준으로 한다. 앞뒤 공백만 정리한다.
새로운 대소문자·유니코드 정규화·이름 합치기 규칙은 넣지 않는다.
같은 키로 귀결되면 복사·삭제하지 않는 변경 없음 처리로 끝낸다. 빈 입력은 기존 UI의 매장명 유지 동작을 따른다.

대상 목록은 `storeKey`, `manualKey`, `bankKey`, `dataKey`, `planKey`, `lastRunKey`의 **여섯 쌍**이다.
원본에 값이 있는 종류만 복사하지만 충돌은 대상 여섯 종류 모두에서 검사한다.
`fc.last`는 현재 값이 원본 매장 식별값일 때만 새 식별값으로 바꾼다. 다른 매장을 가리키면 그대로 둔다.
`fc.breaks`, `fc_use`, 글씨·설치 안내 설정 등 매장별이 아닌 자료는 이동하지 않는다.

### 3. 준비와 복사

1. 변경 전 `UP.store`, `UP.owner`, `UP.manual`, `UP.__plan`, `DATA_SIG` 등 영향받는 상태를 파악한다. 실패 전에 이 값들을 먼저 바꾸지 않는다.
2. 원본 여섯 키·대상 여섯 키·필요한 `fc.last`를 엄격하게 읽는다. 읽을 수 없으면 값이 없다고 가정하지 말고 중단한다.
3. 대상에 자료가 있으면 **쓰기를 시작하기 전에** 충돌을 반환한다. 이름 충돌 검사에 JSON 파싱 성공 여부를 사용하지 않는다.
4. 복사할 내용을 메모리에 준비한다. 분류와 거래내역 JSON의 `store`는 새 이름으로 맞춘다. 같은 저장 버튼에서 바꾼 `owner`도 함께 준비한다. 그 외 내용·판 번호·금액·분류는 보존한다.
5. 내부 이름을 바꿔야 하는 JSON이 깨졌으면 원본을 보존하고 중단한다. 임의 초기화·마이그레이션으로 복구하지 않는다. 다른 자료 통은 원문을 보존한다.
6. 새 키들을 차례로 쓰고 **각 값과 전체 준비된 값이 일치하는지** 다시 읽어 확인한다. 모든 확인이 끝날 때까지 원본 키는 그대로 둔다.
7. 필요한 `fc.last` 갱신과 확인도 성공 판정 안에 포함한다. 실패하면 이전 포인터 복원을 시도하고 원본은 지우지 않는다.

일반 사용자에게 필요한 것은 손실 방지다. 저장 공간이 부족할 때 원본을 먼저 지워 공간을 확보하는 최적화는 하지 않는다.

### 4. 실패와 정리

새 복사나 확인에 실패하면 이번 작업이 만든 대상 키만 제거를 시도하고, 원래 화면 상태를 유지한다.
원래 대상 자료는 사전 충돌 검사로 아예 수정하지 않는다. 롤백용으로 원본을 다시 쓰는 방식은 쓰기 실패 상황에서 복구할 수 없으므로 사용하지 않는다.

정리 자체도 실패할 수 있다. 이때도 원본은 그대로 두고 경고를 표시한다. 남은 대상 조각을 다음 시도에서 기존 자료로 취급하고 임의 삭제하지 않는다.
쓰기 오류로 바뀐 `LS_OK` 등 오류 진단 상태까지 성공 상태로 되돌려 숨기지는 않는다.

새 복사·확인이 전부 성공한 뒤에만 원본 삭제를 시작한다.
이 단계의 원본 삭제가 실패하면 **완성된 새 자료를 롤백으로 지우지 않는다.** 새 매장을 사용하면서 옛 이름 자료 정리가 남았다고 알린다.
다중 키 localStorage는 완전한 트랜잭션이 아니므로 강제 종료·여러 탭 동시 수정까지 원자적으로 보장한다고 쓰지 않는다.
새 영구 저장 키·복구 로그·DB 전환은 이번 범위에 넣지 않는다.

### 5. 저장 버튼과 복원

`drawNames` 저장 처리에서 이름 변경 실패면 즉시 멈춘다. 대표자 변경·`manualLoad`·`savePicks`·`showResult`를 실행하지 않는다.
성공한 경우에만 준비한 이름·대표자와 필요한 캐시 무효화를 반영한다.

이름 변경 경로가 끝난 뒤 기존 `savePicks()`를 무조건 다시 호출하면 내부 `saveData()`의 실패를 놓치는 경로가 생긴다.
이름 변경과 함께 저장할 이름·대표자 메타데이터는 위 저장·확인 단계에 포함하고, 성공 뒤에는 같은 자료를 다시 쓰지 않아도 되게 구성한다.
다른 분류 저장·이름을 바꾸지 않는 대표자 편집의 기존 동작은 넓게 리팩토링하지 않는다.
현재 메모리에만 있는 미저장 자료는 버리거나 저장됐다고 주장하지 않는다. 이 경로가 필요하면 복사 준비 단계에서 기존 형식의 저장 내용을 구성하고 동일한 검증을 거친다.

`fc.data` 안에 옛 store가 남으면 `openSavedData()`가 옛 이름을 복원한다. 키 존재 확인뿐 아니라 **새로고침 후 실제 재개**까지 시험해야 한다.

## 남은 질문과 결정

### 구현 중 정한 작은 선택 (2026-09-29 Claude)

- 저장소 도구는 `00-storage.js` 에 `storeIdOf` · `storeKeysOf`(통 여섯) · `lsRead` · `lsWriteAll` · `lsDropAll` 로 더했다. 기존 `lsGet` 계약은 그대로다.
- `renameStore(oldName, neu, owner)` 는 `{ ok, why, warn }` 를 돌려준다. `why`: `same` · `demo` · `done` · `taken` · `read` · `broken` · `write`. `warn` 은 성공이면 옛 자리 일부가 남음, 실패면 새 자리 일부가 남았을 수 있음.
- 분류·거래내역은 **저장된 원문을 옮기면서 안쪽 `store`·`owner` 만** 새 값으로 바꾼다. 성공한 뒤 `savePicks()` 를 다시 부르지 않는다. 예전 코드는 옮긴 뒤 `savePicks()` 로 메모리 상태를 다시 썼다. 지금은 아직 저장되지 않은 메모리 변경이 있으면 다음 일반 저장 때 새 이름으로 남는다(`DATA_SIG = null`). 그래서 `fc.data` 의 `저장일` 은 그대로이고, `fc.last` 는 원래 이 매장을 가리킬 때만 바뀐다.
- 안쪽 이름을 바꿔야 하는 JSON 이 깨졌을 때(`broken`)는 일반 실패 문구 「이름을 바꾸지 못했습니다 …」를 쓴다.
- 옛 자리 정리만 실패하면 결과 화면으로 가지 않고 편집 화면에 새 이름과 경고를 남긴다.
- `fc.last` 쓰기가 실패했을 때 값이 아직 원래 이름이면 되돌리기 쓰기를 하지 않는다. 막힌 쓰기가 두 번 실패해 경고가 잘못 켜지는 것을 막으려는 것이다.
- 안내 문구의 「매장」 자리는 앱의 호칭 `BIZ.곳`(「사업장」)을 쓴다.
- 같은 저장 이름(`same`)과 예시 화면(`demo`)은 성함 저장 · `savePicks` · 결과 이동으로 이어지는 기존 길을 그대로 탄다.

### 원래 제안 (구현 지시로 확정)

별도 금융 계산·제품 정책 결정 없이 데이터 보존을 우선하는 제안이다.
충돌 이름은 금지하고 앞뒤 공백만 정리하며, 실패 안내 문구는 위 초안을 쓴다.
원본 삭제 실패는 새 자료 보존+정리 경고로 다룬다. 구현 승인과 함께 이 세부 처리도 확정한다.
다중 탭 경쟁·브라우저 강제 종료의 완전한 복구, 모든 저장 동작의 트랜잭션화는 후속 범위다.
